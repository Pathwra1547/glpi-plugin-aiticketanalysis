# Режим MCP: инструменты GLPI только на чтение для AnythingLLM

[English version](mcp-glpi.md) · **Русская версия** · [к README](../README.ru.md)

Эта инструкция объясняет, как дать агенту AnythingLLM возможность смотреть данные в GLPI прямо во
время анализа заявки — и как сделать это, не вручая никому ключи от вашей ITSM-системы.

## 1. Что это такое и чем не является

MCP-сервер **не является частью этого проекта**. Это сторонний npm-пакет:

| | |
| --- | --- |
| **Проект** | [`mcp-glpi` авторства GMS64260](https://github.com/GMS64260/mcp-glpi) |
| **Лицензия** | MIT |
| **Версия, на которую опирается инструкция** | 3.2.0 |
| **Пакет npm** | `mcp-glpi` |

Все заслуги за MCP-сервер принадлежат его авторам. В этом репозитории лежат только:

- эта инструкция,
- файл конфигурации с плейсхолдерами:
  [`anythingllm_mcp_servers.example.json`](mcp/anythingllm_mcp_servers.example.json),
- пример промпта рабочего пространства для прогонов агента:
  [`workspace-prompt-mcp.example.txt`](workspace-prompt-mcp.example.txt).

Если вы распространяете установленный пакет дальше, сохраняйте его файлы `LICENSE` и `README.md` в
неизменном виде — MIT разрешает распространение, но требует указания авторства.

> **Предупреждение про имя файла.** В `.gitignore` плагина намеренно исключён любой файл с именем
> `anythingllm_mcp_servers.json`, потому что настоящий содержит токены GLPI. Держите настоящий файл
> вне системы контроля версий; в репозитории место только плейсхолдеру `.example.json`.

## 2. Как всё это связано

```
Страница заявки GLPI
   └── кнопка «ИИ L3»  ──POST──▶  ajax/analyze.php
                                     │  собирает JSON-контекст
                                     ▼
                        AnythingLLM  /api/v1/workspace/<slug>/chat
                        message = "@agent" + контекст
                                     │
                        агент решает, что нужны ещё данные
                                     ▼
                        MCP-сервер «glpi-readonly» (процесс node,
                        запущенный AnythingLLM внутри своего контейнера)
                                     │  REST API GLPI, токены на чтение
                                     ▼
                                   GLPI
```

MCP-сервер работает **внутри контейнера AnythingLLM**, запускаемый самим AnythingLLM как дочерний
процесс. Это не отдельный контейнер, ему не нужны ни свой порт, ни своя сеть, ни отдельный сервис в
compose. AnythingLLM читает описания MCP-серверов из одного файла в своём каталоге storage и
запускает каждый настроенный сервер по требованию (или при старте, если задан `autoStart`).

## 3. Шаг 1 — включить REST API GLPI и создать токены

Нужны два токена: **App-Token**, идентифицирующий клиентское приложение, и **токен пользователя**,
от имени которого выполняются вызовы.

### 3.1. Включите REST API

**Настройки → Общие → API**. Включите REST API.

### 3.2. Создайте API-клиента и получите App-Token

На той же странице создайте **API-клиента**. Дайте ему узнаваемое имя (например,
`anythingllm-mcp`) и сохраните — GLPI сгенерирует для него **App-Token**.

Заодно ограничьте клиента по **диапазону IP** адресом хоста или сети контейнера AnythingLLM. Это
делается за минуту и заметно снижает ценность украденного токена.

### 3.3. Заведите отдельную учётную запись только на чтение и получите её токен

**Не** используйте персональную учётную запись администратора.

1. Создайте профиль с правами **только на чтение** — по заявкам и тем типам объектов, которые модели
   разрешено смотреть. Права на запись, удаление, очистку и администрирование снимите явно.
2. Создайте пользователя, например `svc-mcp-readonly`, назначьте ему этот профиль и ограничьте теми
   организациями, которые ему положено видеть.
3. Зайдите под этим пользователем (или отредактируйте его) и сгенерируйте **токен API** в разделе
   **Пользователь → Настройки → Ключи удалённого доступа**.

Почему это важно — в [разделе 9](#9-замечания-по-безопасности-специфичные-для-mcp); если коротко,
пакет MCP предоставляет и инструменты записи, и остановить их могут только права GLPI.

## 4. Шаг 2 — установить MCP-сервер внутрь контейнера AnythingLLM

Установите npm-пакет в каталог **storage/plugins** AnythingLLM, чтобы он переживал перезапуски
контейнера и лежал рядом с файлом конфигурации MCP.

Эталонная раскладка, используемая в этой инструкции:

```
/app/server/storage/plugins/
├── anythingllm_mcp_servers.json          ← конфигурация MCP
└── mcp-glpi-runtime/
    └── node_modules/
        └── mcp-glpi/
            ├── dist/index.js             ← точка входа, которую запускает AnythingLLM
            ├── package.json
            ├── LICENSE
            └── README.md
```

Установка прямо в контейнере (`anythingllm` замените именем своего контейнера):

```bash
docker exec -it anythingllm sh -lc '
  mkdir -p /app/server/storage/plugins/mcp-glpi-runtime &&
  cd /app/server/storage/plugins/mcp-glpi-runtime &&
  npm install --omit=dev mcp-glpi
'
```

Если из контейнера нет доступа к реестру npm, соберите каталог на машине, где он есть, и скопируйте
внутрь:

```bash
mkdir -p mcp-glpi-runtime && cd mcp-glpi-runtime
npm install --omit=dev mcp-glpi
cd ..
docker cp mcp-glpi-runtime anythingllm:/app/server/storage/plugins/mcp-glpi-runtime
```

**Используйте именно такую вендорную раскладку, а не `npx -y mcp-glpi`.** Команда `npx` заново
разрешает пакет через реестр npm при каждом старте; на хосте без доступа к реестру MCP-сервер после
этого стабильно падает с таймаутом соединения при запуске.

Проверьте, что Node.js в контейнере достаточно свежий — на эталонном стенде это Node 18:

```bash
docker exec anythingllm node --version
```

## 5. Шаг 3 — написать файл конфигурации MCP

AnythingLLM читает описания всех MCP-серверов из файла
`/app/server/storage/plugins/anythingllm_mcp_servers.json`.

Шаблон лежит в этом репозитории:
[`docs/mcp/anythingllm_mcp_servers.example.json`](mcp/anythingllm_mcp_servers.example.json).

```json
{
  "mcpServers": {
    "glpi-readonly": {
      "command": "node",
      "args": [
        "/app/server/storage/plugins/mcp-glpi-runtime/node_modules/mcp-glpi/dist/index.js"
      ],
      "env": {
        "GLPI_URL": "http://your-glpi-host",
        "GLPI_APP_TOKEN": "YOUR_GLPI_APP_TOKEN",
        "GLPI_USER_TOKEN": "YOUR_GLPI_READONLY_USER_TOKEN"
      },
      "anythingllm": {
        "autoStart": true
      }
    }
  }
}
```

| Ключ | Значение |
| --- | --- |
| `glpi-readonly` | Имя сервера, отображаемое в интерфейсе AnythingLLM. Называйте его по тому, что ему разрешено. |
| `command` / `args` | Запуск `node` по вендорной точке входа. Доступ к реестру при старте не нужен. |
| `GLPI_URL` | GLPI **глазами контейнера AnythingLLM**: `http://glpi` в общей сети Docker, `http://host.docker.internal`, если GLPI на хосте, либо адрес в локальной сети. Не `localhost`: внутри контейнера это сам AnythingLLM. |
| `GLPI_APP_TOKEN` | App-Token из шага 3.2. |
| `GLPI_USER_TOKEN` | Токен API учётной записи только на чтение из шага 3.3. |
| `anythingllm.autoStart` | Запускать сервер вместе с AnythingLLM, а не при первом обращении. |

**Все токены в этом репозитории — плейсхолдеры.** Подставляйте настоящие значения только в
развёрнутой копии и никогда в файл, который вы коммитите.

## 6. Шаг 4 — развернуть и перезапустить

```bash
docker cp anythingllm_mcp_servers.json \
  anythingllm:/app/server/storage/plugins/anythingllm_mcp_servers.json
docker restart anythingllm
```

Если перезапускать контейнер целиком не хочется, AnythingLLM умеет перечитывать MCP-серверы из
интерфейса — см. следующий шаг.

## 7. Шаг 5 — проверить, что MCP поднялся и агент видит инструменты

**Проверьте, что файлы лежат там, где указано в конфиге:**

```bash
docker exec anythingllm ls -la /app/server/storage/plugins/
docker exec anythingllm ls /app/server/storage/plugins/mcp-glpi-runtime/node_modules/mcp-glpi/dist/index.js
```

Оба пути должны существовать. Опечатка в пути — самая частая причина сервера, который так и не
стартовал.

**Проверьте, что процесс живой**, после того как AnythingLLM запустил сервер:

```bash
docker exec anythingllm sh -lc "ps ax | grep -i mcp-glpi | grep -v grep"
```

**Проверьте интерфейс.** В AnythingLLM откройте **Agent Skills → MCP Servers**. Сервер
`glpi-readonly` должен быть в списке и запущен, со списком инструментов, который можно развернуть.
Если он остановлен, используйте кнопку обновления/запуска там же. Если сервер в списке, но с
ошибкой, текст ошибки обычно прямо называет причину (неверный путь, недоступный `GLPI_URL`,
отклонённые токены).

**Проверьте, что агент действительно ими пользуется.** В чате рабочего пространства задайте
проверочный запрос:

```
@agent посмотри в GLPI заявку 1 и скажи её заголовок и статус
```

Если агент отвечает реальными данными из вашего GLPI, цепочка работает целиком. Если он отвечает,
что такого инструмента у него нет, MCP-сервер не подключён к агенту этого рабочего пространства —
перепроверьте страницу Agent Skills.

## 8. Шаг 6 — включить режим агента в плагине

На странице настроек плагина (**Настройки → Плагины → AI Ticket Analysis → значок настройки**), блок
**«Настройки AnythingLLM»**, переведите **«Использовать @agent + MCP GLPI»** в **Да**.

Что это меняет: плагин добавляет к сообщению префикс `@agent`, по которому AnythingLLM понимает, что
запрос нужно прогнать через цикл агента, а не через обычное завершение чата.

Две особенности, о которых стоит помнить:

- **Lite-режим важнее.** Если включён `lite_mode`, режим агента игнорируется полностью: lite-режим
  существует для слабого железа, а прогоны агента — прямая ему противоположность.
- **Поднимите таймаут.** Прогон агента делает несколько обращений к модели за анализ и на локальных
  моделях регулярно занимает минуты. Соответственно увеличьте **«Таймаут запроса (сек)»** (плагин
  допускает до 600 секунд) и таймаут чтения у обратного прокси перед GLPI, если он есть.

Для прогонов агента имеет смысл переключить системный промпт workspace на
[`workspace-prompt-mcp.example.txt`](workspace-prompt-mcp.example.txt) — более короткий вариант на
семь разделов, оставляющий модели запас токенов на вызовы инструментов.

## 9. Замечания по безопасности, специфичные для MCP

**Пакет `mcp-glpi` — не сервер «только на чтение».** Наряду с чтением вроде `glpi_get_ticket`,
`glpi_get_ticket_timeline`, `glpi_list_tickets`, `glpi_get_user` и `glpi_get_knowbase_item` он
предоставляет и инструменты записи — `glpi_create_ticket`, `glpi_add_followup`, `glpi_add_solution`,
`glpi_assign_ticket`, `glpi_create_user`, `glpi_delete_ticket` и другие.

Это не дефект пакета: он задуман как универсальная интеграция с GLPI. Но это значит, что свойство
«только чтение» в данной схеме обеспечивается **исключительно** профилем GLPI, стоящим за
`GLPI_USER_TOKEN`. Если у токена есть права на запись, инструменты записи работают — и единственное,
что стоит между злонамеренно составленной заявкой и изменённым GLPI, это фраза в промпте с просьбой
к модели вести себя прилично. Промпт не является границей безопасности.

Поэтому:

1. **Токен должен принадлежать профилю с правами только на чтение.** Проверьте это, попробовав
   выполнить им запись и убедившись, что GLPI отказывает.
2. **Ограничьте API-клиента по IP** (шаг 3.2).
3. **Держите настоящий `anythingllm_mcp_servers.json` вне системы контроля версий.** В нём два
   токена открытым текстом. Учтите также, что любой, у кого есть доступ к шеллу контейнера
   AnythingLLM, может его прочитать: доступ к контейнеру равносилен доступу к токенам.
4. **Ротируйте оба токена по графику.**
5. **Помните про путь инъекции.** Текст заявки и распознанный текст вложений доходят до агента, а у
   агента есть инструменты. С набором инструментов только на чтение худший исход — «неверный
   ответ»; с инструментами на запись худший исход — «злоумышленник управляет вашей ITSM-системой
   через вашего же помощника». Подробнее — в
   [разделе о безопасности в README](../README.ru.md#9-безопасность).

## 10. Устранение неполадок

### Таймаут соединения при старте

Обычно это конфигурация, запускающая сервер через `npx -y mcp-glpi`: она обращается к реестру npm
при каждом старте, и на хосте без доступа к реестру это всегда провал. Используйте вендорный вариант
с `node` из [шага 3](#5-шаг-3--написать-файл-конфигурации-mcp).

### Таймаут остался и после перехода на `node`

Значит, дело было не в npm, а в сетевом пути до GLPI. Проверьте изнутри контейнера:

```bash
docker exec anythingllm sh -lc 'wget -S -O /dev/null "$GLPI_URL/apirest.php" 2>&1 | head -20'
```

или просто попробуйте тот адрес, который вписали в `GLPI_URL`. Помните, что `localhost` внутри
контейнера AnythingLLM — это сам AnythingLLM, а не GLPI.

### Сервер стартует, но все вызовы отклоняются

Проблема с токенами или настройкой API, в порядке убывания вероятности: REST API не включён в GLPI;
App-Token принадлежит API-клиенту, ограниченному другим диапазоном IP; токен пользователя был
перевыпущен; профиль пользователя не видит организацию, которой принадлежит объект. API GLPI
возвращает содержательную ошибку — прочитайте её в журнале агента AnythingLLM.

### Агент игнорирует инструменты

Проверьте, что MCP-сервер включён для агента именно этого рабочего пространства в разделе
**Agent Skills**, и что плагин действительно отправляет `@agent` (то есть `use_agent_mcp` включён, а
`lite_mode` выключен).

### Прогоны `@agent` очень медленные

Так и должно быть на локальных моделях: агент делает несколько обращений к модели за прогон, и
каждое конкурирует за ту же видеопамять, что и vision-модель. Именно поэтому в плагине
`use_agent_mcp` по умолчанию выключен. Если режим агента нужен регулярно, планируйте больше VRAM или
более быструю модель, а не бесконечно поднимайте таймауты.
